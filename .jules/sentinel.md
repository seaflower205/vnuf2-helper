## 2024-05-28 - Hardcoded Encryption Key in Extension Storage
**Vulnerability:** A hardcoded 15-character key (`VNUF2Helper2026`) was found in `utils/crypto.js`. This key was used to XOR-encrypt user passwords before saving them in the extension's local storage via `chrome.storage.local`.
**Learning:** Hardcoding encryption keys within the source code of an extension is a critical security vulnerability (CWE-798). Since extension source code is fully accessible to anyone who installs it or inspects the unpacked code, a hardcoded key offers no real security. An attacker could simply extract the key and decrypt all user credentials stored by the extension.
**Learning (Code Review):** When updating to a dynamically generated key:
1. **Concurrency/Race Conditions:** If saving multiple credentials concurrently using `Promise.all` while `getKey()` fetches or generates the key asynchronously, multiple random keys will be generated and stored, corrupting the stored data. `getKey()` must use a promise cache/memoization to ensure the same key is returned to all concurrent requests.
2. **Backward Compatibility:** Existing users will have passwords stored using the old hardcoded key. If the system immediately tries to decode them with the new dynamic key, the passwords will be corrupted, resulting in login failures. A versioning scheme (e.g., prefixing new passwords with `v2:`) is required so that legacy passwords can still be decoded using the old hardcoded key until they are re-saved.
**Prevention:** Keys should never be stored in source code. A better pattern for browser extensions is to dynamically generate a cryptographically secure random key on first run (using `crypto.getRandomValues`), store that key securely in the extension's local storage (`chrome.storage.local`), and fetch it asynchronously (with caching to prevent race conditions) when encryption/decryption is needed. Ensure backward compatibility via versioning.
